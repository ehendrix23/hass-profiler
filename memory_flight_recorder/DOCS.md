# Memory Flight Recorder

Requires HAOS amd64 and the existing 15-second Glances telemetry entity IDs listed in `ha_feed.py`. System Monitor available memory is an independent measurement. Verify these entities exist before starting. A filtered WebSocket subscription uses the Supervisor's HA API proxy; a separate short-lived connection calls only the companion's profiling action when authorized by the detector. No additional Glances or Recorder polling. No exposed network ports, Docker socket, host PID access or full access. Keep Protection mode on.

The recorder settles sequential updates for two seconds and labels unchanged carried-forward values. This does not guarantee that each component value is from precisely the same source cycle. The independent available-memory reading is rejected if too old. Check `/share/Logs/memory-watch/status.json` for source freshness, connection, active recording and buffer count. The health report is written approximately every 60 seconds.

The rolling buffer is capped at 128 samples/30 minutes. An incident records while abnormal flags persist and for 15 minutes afterward. Journals are fsynced per record, rotate at 1 MiB, and have a 100 MiB total incident cap, 30-day retention and 256-file limit. The App never restarts Core or performs automated remediation. Previous evidence remains under `/share/Logs/memory-watch/`; it may be included in system backups. Do not run two recorder instances with the same output directory.

## Actual in-Core profiling

Install the repository's `core_companion/hass_profiler.py` into `/config/pyscript/`; require Pyscript with `allow_all_imports` enabled. Verify action `pyscript.hass_profiler_memory` before starting the App with `automatic_memory_profiling: true` (default). Set `profile_seconds` to 5–60 seconds (default 15). A fresh rapid-growth, rising-high-memory or first absolute-high-memory flag can request a profile with available memory at least 1800 MiB and free swap at least 800 MiB. One request at a time, minimum 60 seconds between requests, at most three requests in five minutes; the attempt budget is persisted before dispatch. The companion independently checks live Linux headroom and process RSS and owns/stops the tracer. It aborts on pressure or tracing budgets, and can preserve a partial allocation summary when snapshotting remains safe. No automatic GC census or full heap scans.

The companion takes a traceback snapshot of allocations made since tracing began and still live when the snapshot is taken. Attribution uses the nearest matching HA integration or custom component traceback frame. It is not cumulative allocated volume, retained pre-existing heap ownership, or total integration RSS. Unattributed Python bytes and native allocations remain distinct. The optional manual GC census reports shallow sizes of instances of integration-defined classes, not transitive ownership. Manual action accepts `seconds` and `include_census`; omit census during pressure. Reports are limited to 64 KiB, 64 files and 30 days; they contain integration/module names, source basenames and line numbers, numeric data, not object values. Core writes each report atomically. The controller checks it against the service response and records the result and filename in the incident and `profile-control.json`. `status.json` exposes the latest profile outcome. A skipped or unverified result is not successful attribution. Existing incident journal limits are unchanged (100 MiB; profiles have a separate maximum of 4 MiB). Never run simultaneous collectors sharing this directory.

## Tests

From this directory: `python -m pip install websockets==16.0`, then `python -m unittest -v test_flight_recorder test_ha_feed test_profile_control`. Run the companion tests with `python -m unittest discover -s ../core_companion`. The procfs tests require Linux. Replay fixtures are synthetic; the WebSocket protocol tests simulate HA as an external boundary. Live in-Core acceptance requires a real persisted profile, not just a successful simulated service response.
